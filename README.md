**Genestrip-DB** - a selection of databases for [Genestrip](https://github.com/pfeiferd/genestrip)
===============================================
  
This project contains some configuration files and a few scripts in order to 
generate [databases and indexes](https://github.com/pfeiferd/genestrip/blob/master/README.md#generating-your-own-database) for metagenomic analysis via [Genestrip](https://github.com/pfeiferd/genestrip).

## Building and installing

Genestrip-DB requires [Maven 3](https://maven.apache.org/) and the [JRE](https://jdk.java.net/) 11 or higher.

To build the databases and indexes, `cd` to the installation directory `genestrip-db`. Given a matching Maven and JDK installation, `sh bin/makedbs.sh` 
will generate 11 databases (and indexes) of different sizes. The generation process is resource intensive and may take several days for all databases.
Generating the bacterial databases is particularly time consuming.

Each project yields two databases. `<project>_db.zip` is the Genestrip database, and `<project>_ftdb.zip` is the same database with the
taxonomy refined below the genus rank by [Genestrip-FT](https://github.com/pfeiferd/genestrip/blob/master/ft/README.md), which raises
the accuracy of a `match` under that rank. The script asks for the goals
[`ftgenall`](https://github.com/pfeiferd/genestrip/blob/master/ft/Goals.md),
[`svgtaxtree`](https://github.com/pfeiferd/genestrip/blob/master/Goals.md) and
[`ftsvgtaxtree`](https://github.com/pfeiferd/genestrip/blob/master/ft/Goals.md) and thereby generates both databases and both tree
images of a project in one run; other goals may be passed as arguments, e.g. `sh bin/makedbs.sh genall` for the plain databases alone.
The refinement step also writes the *k*-mer index `<project>_storekmerindex.ser.gz` and adds to the time, the memory and the disk space
the generation takes.

The tree images show the contents of the generated databases: `<project>_svgtaxtree.svg` for the plain and `<project>_ftsvgtaxtree.svg`
for the FT database, both in the project's `csv` folder. The indentation of a node reflects the number of *k*-mers stored for it, where
the node with the most *k*-mers is indented by
[`svgKmerNodeIndentFactor`](https://github.com/pfeiferd/genestrip/blob/master/ConfigParams.md) pixels, which `data/config.properties`
sets to 1000.

The databases are generated with [`dataNodes=true`](https://github.com/pfeiferd/genestrip/blob/master/ConfigParams.md), so the *k*-mers
of a taxon are stored at an artificial child node of rank `DATA` instead of at the taxon itself. The trees and the result files of a
`match` hence show a node `Data for <taxid>` below each taxon that contributes *k*-mers.

Your machine should have:
* 1.5 TB of free disk space - mainly for downloading genomes from [NCBI](https://www.ncbi.nlm.nih.gov/),
* at least 8 cores - the more the better (some phases of the database generation keep 32 cores 100% busy),
* 48 GB of main memory,
* a high bandwidth Internet connection.

The databases are based on and compatible with [Genestrip 4.0](https://github.com/pfeiferd/genestrip/releases/tag/v4.0). A database generated by an earlier version of Genestrip cannot be read by Genestrip 4.0 and must be generated anew.

The database `borrelia_plasmid` has no configuration in this project at present: `bin/makedbs.sh` does not generate it, and `bin/matchticks.sh` can only match against it where it is already in place.

Note that Genestrip's [`updatedb`](https://github.com/pfeiferd/genestrip/blob/master/Goals.md)-phase accounts for unspecific *k*-mers and largely avoids false positive counts during `match`es.
To further reduce false positives, all databases except for `plasmopara`, `protozoa_rna`, `tick-borne_rna` and `vineyard` are built such that *k*-mers also occurring in the [human genome](https://ftp.ncbi.nlm.nih.gov/genomes/all/GCA/000/001/405/GCA_000001405.29_GRCh38.p14/GCA_000001405.29_GRCh38.p14_genomic.fna.gz) 
are [pushed to the least common ancestor](https://github.com/pfeiferd/genestrip/blob/master/README.md#manually-adding-fasta-files).

## Testing the databases `borrelia`, `borrelia_plasmid` and `tick-borne`

The script `bin/matchticks.sh` [runs the Genestrip goal `match`](https://github.com/pfeiferd/genestrip/blob/master/README.md#usage-and-goals) for 8 fastq files taken from [this publication](https://www.ncbi.nlm.nih.gov/pmc/articles/PMC10328957/).
To do so, the fastq files will be [streamed](https://github.com/pfeiferd/genestrip/blob/master/README.md#reading-streaming-and-downloading-fastq-files) from the corresponding [NCBI server](https://www.be-md.ncbi.nlm.nih.gov).
As expected, Genestrip finds DNA from borrelia and other tick-borne infections accordingly.

## Downloading the ready-made databases

If you don't want to generate them yourself, the databases and indexes can also be [downloaded from genestrip.it.hs-heilbronn.de](https://genestrip.it.hs-heilbronn.de/files/data).
The [`projects` folder](https://genestrip.it.hs-heilbronn.de/files/data/projects/) corresponds 
to the [`projects` folder's](https://github.com/pfeiferd/genestrip-db/tree/master/data/projects) state of this project, after the script `bin/makedbs.sh` has run successfully based on the [RefSeq Release 234](https://ftp.ncbi.nlm.nih.gov/refseq/release/RELEASE_NUMBER). That upload stems from the Genestrip version this project required when it was made, which need not be the current one.
The upload covers each project's `csv` folder, so `<project>_svgtaxtree.svg` and `<project>_ftsvgtaxtree.svg` can be viewed there without generating a database.

The script `bin/upload.sh` performs that upload. It transfers everything below `data/projects` - the folder `projects` itself included - to a
mirror given as its first argument, e.g. `sh bin/upload.sh user@host:/var/www/files/data/`. The files go there as they are: nothing is
packed or copied beforehand, and `rsync --inplace` writes into the target file directly, so neither the generating machine nor the mirror
needs room for a second copy of a database. The checksums `data/projects/md5sums.txt` are written by `bin/md5.sh`, which `bin/makedbs.sh`
calls at the end of a default run and `bin/upload.sh` calls again where a file is newer than they are. An interrupted upload may simply be repeated: only what is missing or has changed since is transferred again.
